# 2026-08-29 — Terrain / map-tile array hunt

**Result: FOUND, and with it the whole seven-layer map-buffer block, the map's true
dimensions as a direct read, and the complete terrain ID → name table.**

**Provenance for every live observation below: Chapter 22 "Kinship's Bond", Hector Hard
Mode, turn 1 player phase.** (The chapter title was read off the save-file screen —
`"Ch. 22: Kinship's Bond"` in the text buffer — which also confirms RAM.md's existing
"Ch.22 Hector HM" label for this board. 22 × 23 map, 12 deployed, 36 enemies, 7 green.)

---

## What worked, in order

### 1. Dump all of RAM to disk in one shot (0.2 s)

The single biggest speed-up of the run, and it should be the default for any future hunt.
`lua/bridge.lua`'s `process_buffer` drains **every** buffered request each frame, so
requests can be pipelined. A Node script that fires 8 + 64 `read_range` calls with
`Promise.all` dumps IWRAM (32 KiB) and EWRAM (256 KiB) in **0.2 s wall-clock**, versus
~15 min of one-at-a-time MCP round trips.

```js
import { MgbaClient } from "<mcp-mgba>/dist/mgba.js";
const m = new MgbaClient("127.0.0.1", 8765);
const proms = [];
for (let off = 0; off < 0x40000; off += 4096)
  proms.push(m.call("read_range", { address: 0x02000000 + off, length: 4096 }));
const ewram = Buffer.concat((await Promise.all(proms)).map(Buffer.from));
```

Analyse the dumps locally. Round-trip count stops being the binding constraint.

### 2. Sweep the dumps for the row-pointer-table *shape*

Exactly the approach the previous session recommended. For every 4-aligned address `T`:

```
w0 = u32(T);  n = (w0 - T) / 4;  s = u32(T+4) - w0
accept iff  w0 > T,  (w0-T) % 4 == 0,  5 <= n <= 80,  6 <= s <= 80,
            and u32(T + 4*i) == w0 + s*i  for every i in [0, n)
```

Over IWRAM + EWRAM this returned **exactly 8 hits, no noise**:

| Table | Rows | Stride | Data | What it turned out to be |
|---|---|---|---|---|
| `0x03000440` | 27 | 24 | `0x030004AC` | movement cost (already known) |
| `0x03000BF8` | 27 | 24 | `0x03000C64` | range overlay |
| `0x0202E3F8` | 27 | 24 | `0x0202E464` | **unit occupancy** |
| `0x0202EBB0` | 27 | 24 | `0x0202EC1C` | **TERRAIN** |
| `0x0202F368` | 27 | 24 | `0x0202F3D4` | fog / vision (all `0x01`) |
| `0x0202FB20` | 27 | 24 | `0x0202FB8C` | all zeros |
| `0x020302D8` | 27 | 24 | `0x0202FB8C`+ | all zeros (already known) |
| `0x02032E90` | 24 | 44 | `0x02032EF0` | tile-graphic map, u16 per tile |

The five EWRAM layers sit at a fixed **`0x7B8` stride**: `0x0202E3F8`, `0x0202EBB0`,
`0x0202F368`, `0x0202FB20`, `0x020302D8`.

### 3. Read the layer catalogue out of the ROM literal pool

Searching the ROM **file on disk** (no emulator needed) for each table address as a
32-bit literal found them all clustered in one pool, which is the map-buffer init
function's:

```
0x08018E44: 0x0202E3F8   unit    table      0x08018E48: 0x0202E3DC  &gBmMapUnit
0x08018E4C: 0x0202E3D8   &gBmMapSize
0x08018E50: 0x0202EBB0   terrain table      0x08018E54: 0x0202E3E0  &gBmMapTerrain
0x08018E58: 0x03000440   movement table     0x08018E5C: 0x0202E3E4  &gBmMapMovement
0x08018E60: 0x03000BF8   range   table      0x08018E64: 0x0202E3E8  &gBmMapRange
0x08018E68: 0x0202F368   fog     table      0x08018E6C: 0x0202E3EC  &gBmMapFog
0x08018E70: 0x0202FB20   hidden  table      0x08018E74: 0x0202E3F0  &gBmMapHidden
0x08018E78: 0x020302D8   other   table      0x08018E7C: 0x0202E3F4  &gBmMapOther
```

**This is why these addresses cannot be per-chapter: they are compile-time constants.**
Only the row count and stride are sized per map, and you never need them anyway because
the seven pointer slots at `0x0202E3DC`–`0x0202E3F4` already hold `table + 8`, i.e.
`&table[2]`, so the `+2` border offset is pre-baked.

`0x0202E3D8` is `gBmMapSize`: `u16 width`, `u16 height`. Read `0x00170016` here
= 22 × 23, matching the movement grid's `stride-2` / `rows-4` derivation exactly.

### 4. Prove it, four independent ways

**(a) `fe7_inspect` on real tiles — 10 tiles, 10 distinct terrain values, 10/10 correct.**

| Tile | array byte | readout |
|---|---|---|
| (18,0) | `0x01` | `"Plain."` |
| (0,8) | `0x0C` | `"Forest"` |
| (12,2) | `0x17` | `"Floor."` |
| (12,3) | `0x1A` | `"Wall"` |
| (15,11) | `0x1B` | `"Wall"` |
| (13,7) | `0x1D` | `"Pillar"` |
| (17,9) | `0x1E` | `"Door"` |
| (4,17) | `0x21` | `"Chest."` |
| (11,5) | `0x2D` | `"Stairs"` |
| (9,4) | `0x3F` | `"Brace."` |

**(b) Against RAM.md's own earlier forecast readings on this same chapter.** The combat
forecast section records terrain ID `29` at `(8,7)` (with `terrainDef=1`, `terrainAvo=20`)
and terrain ID `23` at `(9,6)` and `(11,6)`. The array reads `0x1D`, `0x17`, `0x17` at
exactly those three tiles. Two sessions, two unrelated mechanisms, same numbers.

**(c) Against `fe7_reachable`'s cost map.** Every `0x1A`/`0x1B` (Wall) and `0x3F` (Brace)
tile inside Hector's range is `0xFF`; every `0x17`/`0x01`/`0x2D` tile costs 1 per step.

**(d) Causal — write to the array and watch the game obey.** This is the decisive one.
With Hector (slot 0) at (11,2):

```
write8( terrain(12,2), 0x0C )   # Forest
write8( terrain(11,3), 0x1A )   # Wall
```

- `fe7_inspect` then reported `"Forest"` at (12,2) and `"Wall"` at (11,3)
- `fe7_reachable(slot 0)` cost at (12,2) went **1 → 2** (forest costs 2)
- (11,3) went from cost 2 to **unreachable**
- (11,5) went **3 → 5**, because the path had to detour around the new wall

So it is not a copy or a render cache — it is the array the pathfinder and the cursor
readout both read.

### 5. Complete the terrain ID → name table by writing IDs and reading the name back

Write ID *n* into one empty tile, walk the cursor onto it, read `0x0202A5B4`. Batched 22
at a time along row `y = 0` (all 22 tiles unit-free on this map), restoring the row
afterwards. Full table in RAM.md. Valid range is **`0x00`–`0x40`**; `0x41` returns an
empty string and `0x42`+ returns garbage or hangs/corrupts the game (see below).

## Negative results and things that cost time

- **Writing terrain IDs ≥ `0x41` corrupts the game.** The first batched sweep wrote
  `44..65` at once, which included `0x42`+, and the game went off the rails: the unit
  arrays filled with garbage (`cls-1`, HP 8/183, coords (28,215)), `gBmMapSize` read
  `27649 x 18464`, and `fe7_inspect` hung. Recovered by loading a save state.
  **The safe range is `0x00`–`0x40` inclusive.** The redone sweep saved/reloaded a state
  per ID and wrapped `fe7_inspect` in a 20 s timeout, which handled it cleanly.
- **Searching the ROM for the terrain Avoid / Def bonus lookup tables failed.** Filters
  requiring `tbl[0x0C] == 20 && tbl[0x1D] == 20 && tbl[0x17] == 0 && tbl[0x01] == 0`
  (avoid) returned **zero** candidates; the Def variant (`tbl[0x0C] == 1`,
  `tbl[0x1D] == 1`, `tbl[0x0A] == 2`) returned 2, neither of which looks like terrain
  data. Either FE7 does not store these as flat `[terrainId]` byte arrays, or the
  assumed bonus values are wrong. The bonuses are readable per-tile from `BattleUnit
  +0x56/+0x57` anyway. **Do not repeat this search as specified**; a better lever is to
  disassemble the code that fills `BattleUnit +0x55..+0x57`.
- **`0x0202FB20` and `0x020302D8` are all zeros** on Ch.22 turn 1 — matching the earlier
  Ch.7 finding for the latter. `0x0202F368` is uniformly `0x01`. None of the three is
  terrain.
- **The second-map check could not be completed on a differently-sized *playable* map.**
  Route attempted: hard reset → title → save-file list → load. The only save file on the
  cartridge is `"Ch. 22: Kinship's Bond"` — the same chapter — so loading it reproduces
  the same 22 × 23 board (which it did, at the same addresses, after a full reset: a
  useful re-verification, just not of a different size). Menu navigation is close to
  blind: the decoded-text buffer at `0x0202A5B4` **does not refresh on most title-screen
  transitions**, so `Down`/`Up` on the file list are unobservable. What did work as a
  progress signal was watching `gBmMapSize` go `0 → nonzero` and dumping the EWRAM
  ASCII strings.
  - One partial data point: during the chapter-intro cutscene, `gBmMapSize` briefly read
    **15 × 11**, and 11 rows of 15 bytes decoded cleanly through the same
    `0x0202E3E0` pointer array. Different geometry, same globals, coherent read — but
    its *content* was never checked against an oracle, so this is Unverified.
- **`fe7_state` "phase 0x08 / cursor (17987,2048)" is the crash signature.** Worth
  recognising: if the roster shows `cls-1` at (28,215) with HP 8/183, the CPU is in the
  weeds and only a state load will help.
- The battery save's suspend data was erased along the way ("Suspended data will be
  lost." → Yes). Restored from a byte-for-byte backup taken before the run.

## Loose end noticed, not chased

At the **Preparations** screen of this chapter, `(10,4)` and `(11,4)` read `0x1A` (Wall);
on **turn 1** of the same chapter they read `0x17` (Floor). Everything else in the grid is
identical. So the terrain array is **mutable at runtime** — something in the opening event
opens that gap. Unverified as to cause, but it means a cached terrain map must be
invalidated, not read once at map load.

## Addendum — second map, same day: Lyn Ch.7 "Siblings Abroad" (20 × 14)

Grant loaded Ch.7 specifically to close the one residual risk: the **field order inside
`gBmMapSize`**. Ch.22 is 22 × 23 (taller than wide), so the two `u16`s could only be told
apart by cross-referencing the movement table. Ch.7 is **wider than tall**, which makes a
swapped decode impossible to miss.

```
read_range(0x0202E3D8, 4) -> 14 00 0E 00     # width = 0x0014 = 20, height = 0x000E = 14
```

| Source | width | height |
|---|---|---|
| `gBmMapSize` direct read | 20 | 14 |
| terrain table `0x0202EBB0` (18 rows, stride 22) → `stride-2` / `rows-4` | 20 | 14 |
| movement table `0x03000440` (18 rows, stride 22) | 20 | 14 |
| this file's previously recorded Ch.7 geometry | 20 | 14 |

Bounds are exact in both directions: the two pad bytes ending each row read `00 00`, and
row `y = 14` (first past the map) is entirely zero.

**Width first. Confirmed on two maps of opposite aspect ratio.**

Free corroboration from the same read:

- The seven pointer slots hold **byte-identical values on both chapters**
  (`0x0202E400`, `0x0202EBB8`, `0x03000448`, `0x03000C00`, `0x0202F370`, `0x0202FB28`,
  `0x020302E0`). Expected — each is `&table[2]`, an offset of two *pointers*, independent
  of map size — but it confirms the static bases live on two differently-sized maps rather
  than from the ROM literal pool alone.
- Ch.7's terrain decodes as a coherent outdoor map using the Ch.22-derived ID table:
  `0x11`/`0x12` Mntn/Peak in a contiguous range, `0x10` River with `0x13` Bridge tiles
  sitting *inside* it at (17,4), (13,5), (11,9), (13,12), `0x0A` Fort ×4, `0x05` House,
  `0x07` Vendor, `0x26` Cliff on a clean diagonal, `0x03` Village at (17,2) on a chapter
  Grant confirmed has a village. **Not oracle-checked with `fe7_inspect`** (out of scope
  for this pass), so Inferred — but every one of these IDs is absent from Ch.22's castle
  set, so it is meaningful evidence that the encoding is not map-specific.

Read-only pass; nothing was written and no state was loaded or saved.
