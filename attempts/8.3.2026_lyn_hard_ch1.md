## Rule amendment (2026-08-08): labeling screenshots

Screenshots are now permitted for **one** purpose: attaching a human-readable label to a
value **already located in memory**. They may never be used to *locate* a value, and never
to read state during actual play.

Rationale: memory yields numbers, not names. Menu labels and objective text are
tile-rendered and compressed rather than stored as ASCII, so reading them from RAM would
require reverse-engineering the text engine. Meanwhile a *wrong* label is worse than a
missing one — see the `0x0202BC0A` regression, where a confident wrong entry cost a whole
re-derivation.

Every use is logged here with the address it labeled, so the rule is auditable rather than
dependent on my self-report.

## Phase 1 — Menu system (SOLVED, memory only)

Struct layout, confirmed across two instances:

```
+0x00  u8  entry count
+0x01  u8  highlight index (0-based, wraps)
+0x02  u8  index mirror
+0x03  u8  state: 0x01 = open/active, 0x05 = closed/dismissed
```

| Menu | Address | Observed count |
|---|---|---|
| Field menu (Unit/Status/Options/Suspend/End) | `0x020252C0` | 5 |
| Unit action menu (Lyn, no adjacent enemy) | `0x02025470` | 2 |

**Method:** open the menu → `snapshot_memory(EWRAM)` → press Down →
`diff_memory(predicate=increased, width=1)`. The index falls out as a clean `0 → 1`, with
its mirror alongside. Verified by a second Down (`→ 2`) and two Ups (`→ 0`).

**Wrap confirmed:** Up from index 0 on the 5-entry field menu lands on **4**. This proves
from memory what was previously only asserted from a screenshot: `["A","Up","A"]` is a
structurally safe end-turn, because Up from the top entry can only reach `Unit` or `End`,
never `Suspend`.

**Staleness caveat:** count and index keep stale values after a menu closes. Only `+0x03`
distinguishes open from closed. Never infer "a menu is open" from a plausible-looking count.

Secondary signal: the highlight is drawn as tile rows near `0x020235A4` / `0x02023624`,
stride `0x80`. Not needed for control, but an independent confirmation that a menu moved.

## Phase 2 — "Has acted", phase indicator, menu labels

### "Has acted" flag — FOUND (on enemies)

```
unit +0x43  u8   0 → 1 once the unit has acted this phase
unit +0x45  u8   0 → 1 likewise
```

**Evidence:** after the turn-2 enemy phase, *both* brigands read `+0x43 = 1` and `+0x45 = 1`
against a baseline of `0`. Crucially, **Brigand A never moved** (still at `(3,2)`) and still
got both flags — so this marks *acted*, not *moved*. Lyn read `0` on both during the fresh
player phase.

**Confidence: Confirmed for enemies. UNTESTED on player units** — Lyn is the only
deployable unit in this chapter, so her acting immediately ends the player phase and
refreshes her before the flag can be sampled. Also unresolved: why *two* bytes rather than
one. Plausibly moved-vs-acted, but that's a guess.

### Last-acted-unit record — `0x0202BD48`

Sits 8 bytes *before* the player unit array.

```
0x0202BD48  u32  roster index of the unit that last acted   (0x01 Lyn → 0x82 Brigand B)
0x0202BD4C  u16  x of the tile it acted FROM                (13 → 2)
0x0202BD4E  u16  y                                          (7 → 6)
```

**Inferred.** Stores the *origin* position, not the destination, which suggests it backs the
move-undo feature.

### Phase auto-advance (important for automation)

Because Lyn is the sole player unit, the instant she acts the player phase ends, the enemy
phase runs, and the turn counter advances. **There is no observable "player phase with all
units spent" state in this chapter.** Any automation that waits for one will hang.

### Brigand movement — Confirmed

Brigand B moved `(2,6) → (7,6)` on the turn-2 enemy phase: 5 tiles, matching Brigand move 5.
Brigand A stayed at `(3,2)`. Read directly from `+0x10`/`+0x11`.

### Phase indicator — NOT FOUND

Attempt was inconclusive. Two things spoiled the sample: turn-2 scripted dialogue absorbed
my inputs, and the auto-phase-advance above meant I could never catch a clean mid-enemy-phase
read. **Noting the gap rather than guessing.** Retry needs either a chapter with multiple
deployable units, or a tight poll loop fired immediately on phase change.

## Menu system — REVISED (and a correction to Phase 1)

**Menus are allocated dynamically.** Observed slots: `0x020251E8`, `0x020252C0`,
`0x02025470`. The *same* logical menu (Lyn's action menu) appeared at `0x020252C0` in one run
and `0x020251E8` in another. Hardcoding an address does not work.

**CORRECTION.** Phase 1 recorded `+0x03` as `0x01 = open, 0x05 = closed`. **That is not
reliable.** `0x020251E8` read `state = 0x05` while its menu was demonstrably live — the very
next `A` press selected its index-0 entry and opened the item list. Downgraded to
**Unverified**; do not gate decisions on it.

**The rule that does work** — locate the live menu by behaviour, not address:

```
snapshot_memory(EWRAM)
press Down
diff_memory(predicate=changed, width=1)
  → the index byte and its mirror appear as an adjacent pair
  → read count at (index address - 1)
```

Three calls per menu, but correct regardless of where the menu was allocated.

### A second correction: "the input didn't register"

Twice I concluded a press hadn't landed because both known slots read `0x05`. **Both times I
was wrong** — the presses *were* registering, into a slot I wasn't watching. I only caught it
when an `A` press opened the item list, which is only reachable from a live action menu.

Worth recording as a method lesson: **"the input didn't land" and "I'm reading the wrong
address" are indistinguishable from a single read**, and I guessed wrong both times. Confirm
via an *effect* (menu contents, unit position, turn counter) rather than via the absence of a
change at an address I merely expect to be correct.

## Findings

### Three unit arrays — a complete census

One search for character pointers over all of EWRAM returned **93 matches in three
perfectly-strided groups**, so this is exhaustive rather than a sample:

| Base | Slots | What |
|---|---|---|
| `0x020106DC` | 29 | **new** — roster mirror, byte-identical to the player array here |
| `0x0202BD50` | 29 | player array |
| `0x0202CEC0` | 35 | enemy array |

**No NPC/green array exists** — an 8 KiB sweep past the enemy array returned zero, and the 93
pointers are fully accounted for. That closes a question `RAM.md` had carried as "may simply
have been empty." Still worth re-checking on a map with actual green units.

### The roster mirror is the interesting one

`0x020106DC` is byte-for-byte identical to the live player array at Preparations. It's either
the persistent party list or a chapter-start backup for the restart feature — prep can't tell
them apart, since both predict identical contents. **Test queued:** damage and move a unit on
the map, then compare. Frozen ⇒ backup; tracking ⇒ active mirror.

### Deployment is encoded as `x = 0xFF`

The player array holds the **whole 29-unit roster**, not just deployed units. Slots 0–10 had
real map coordinates; slots 11–28 all read `x = 0xFF`. Bit 3 of the `+0x0C` flags also flips
for benched units.

Consequence worth noting: the array is **not** a deployed-unit list, so any automation
iterating it must filter on `x != 0xFF` or it will try to move units that aren't on the map.

### Class IDs are now computable

`class ID = (class_ptr - 0x08BE015C) / 0x54`, validated by back-testing the Lyn-mode Brigand
pointer to exactly `0x39` — a value derived independently in an earlier session. Slots 0/1/2
compute to classes 3/1/2 with roster indices 1/2/3, i.e. Hector / Eliwood / Lyn.

The analogous character-ID formula **does not check out** and is recorded as a contradiction in
`RAM.md`: the unit carrying Lyn's unique Lord class has a character pointer mapping to ID
`0x2D`, not `0x03`. Left unresolved rather than papered over.

### Player array base settled

A backward search from `0x0202BC00` found no character pointer before `0x0202BD52`,
**disproving** the old speculation that the true base was `0x0202BD08`.

### Preparations menu uses a different struct

```
0x0202543A  u8  highlight index
0x0202543B  u8  entry count (5)
```

Count comes *after* index — the reverse of in-map menus. So the struct layout is **not**
universal; find the index by diff, then inspect neighbours in both directions.

### Gold — candidate, not confirmed

`0x0202BC00` held 7336, unique in EWRAM. Gold isn't shown at Preparations so it stays
**Unverified**; the settling test is a spend-and-diff at an on-map vendor.

## Method lesson: the adjacent-pair false positive

In-map menus keep index and mirror adjacent, so "two neighbouring bytes both changed" felt like
a reliable signature. On the prep screen it was wrong: `0x02024F16`/`0x02024F17` both increased
to 2 and looked exactly like an index+mirror pair, but they are the **high bytes of a pointer**
(`0x020254E8`) that happened to move.

What actually worked was **two-step consistency**: press Down twice and keep only addresses
reading 1 then 2. That eliminated all four false candidates and left one correct answer. A
single transition is not enough evidence — this is the same failure mode as the original
`0x0202BC0A` cursor mistake, in a new costume.

# Phase 4 — Ch.22 map phase

Entered the battle from Preparations (`Start` → a few `A` presses to clear the opening event).
Turn counter went to 1, cursor on Hector at `(11,2)`.

## Phase indicator — SOLVED: `0x0202BC07`

The blocker that Lyn Ch.1 structurally could not deliver. Polled a single byte across a turn
boundary and got the **complete cycle**:

```
0x00 player (turn 1)  ->  0x80 enemy  ->  0x40 green  ->  0x00 player (turn 2)
```

Values are FE7's faction constants (blue `0x00`, green `0x40`, red `0x80`), which corroborate the
roster-index convention already documented (player `0x01+`, enemy `0x81+` = faction base + index).

Two things fell out of this:

- **The green phase runs even with zero green units on the map.** An earlier session saw this
  byte flick to `0x40` in Lyn Ch.1 and recorded it as an unexplained "transient flag." It was the
  empty green phase all along.
- **This is the correct wait condition for automation.** Poll until `0x00`. Do not use the turn
  counter (it increments on *return* to the player phase) and do not use wall-clock delays.

## Player-side has-acted — SOLVED: `+0x0C` low byte = `0x42`

Moved Hector `(11,2) → (12,2)` and chose Wait. The narrow diff over the player array returned
exactly **2 changes**: his x, and his `+0x0C` flags going `0x00 → 0x42` (bits 1 and 6).

The control that makes this airtight: **Eliwood, in the same array at the same instant, read
`0x00`.** Same-moment comparison beats before/after when the surrounding state is noisy.

Bit 0 (`0x01`) is separate and transient: it means *selected / in motion*.

## Correction: `+0x43` / `+0x45` are NOT has-acted

An earlier session recorded these as the has-acted marker, "Confirmed for enemies." **Wrong.**
Hector's entire `+0x40..+0x47` range read all zeros after he acted.

The original evidence misled for a specific, instructive reason: the enemy sample was taken
*after* the enemy phase ended, and **units are refreshed at the start of the enemy phase** — so
the real flags had already been cleared, while `+0x43/+0x45` persisted and looked like the
answer. They are something that survives a phase change, which has-acted by definition does not.

Verified the refresh timing directly: Hector's `0x42` had already cleared to `0x00` by the time
the phase byte read `0x80`.

## Roster mirror — SOLVED: frozen chapter-start backup

`0x020106DC` kept `x=11 / flags 0x01` while live Hector read `x=12 / flags 0x42`, and a diff over
its full region reported **zero** changes. It does not track live state.

Useful side effect: it's a free "what did this unit look like at chapter start?" reference for
computing damage taken or distance moved.

## Terrain — SOLVED, and better than expected: `0x0202A5B4`

Hunting terrain turned up something much more valuable. **FE7 decompresses text into a
plain-ASCII buffer in RAM**, and the first string in it is the terrain name under the cursor:

| Cursor | String |
|---|---|
| `(11,3)` | `"Floor"` |
| `(11,6)` | `"Floor"` |
| `(6,6)` | `"Wall"` |

The same buffer also held `"Nils"` and the dialogue line *"We'll serve as your reinfo[rcements]"*.

So terrain is queryable **by name**, one read per tile, with no screenshot and without locating
the numeric tile array. The numeric terrain ID and underlying map array remain unlocated, but

**This likely obsoletes the labeling-screenshot allowance.** If menu labels also route through
this buffer, screenshots become unnecessary entirely.

## A costly detour worth recording

Between the phase discovery and the terrain work I lost track of the game state for roughly a
dozen calls. Turn 2 fired a scripted event; `Up`/`Down` were silently swallowed while `A`
advanced text. From a single read, **"input was ignored" and "I'm reading a stale address" look

What eventually diagnosed it, all from memory:

- A direction press produced **~10 changes and no cursor bytes**; a working cursor move produces
  **~41 changes including `0x0202BBCE`**. The signature difference is the tell.
- `A` produced **411** changes with an incrementing tile pattern — a window being drawn.
- `0x0202BBCC` and `0x0202BBD0` had **diverged** `(12,8)` vs `(11,2)`; two `B` presses unwound the

That divergence is now recorded in `RAM.md` as a cheap "is the cursor under my control?" probe.
**The real gap is that no known address says "dialogue is active"** — that's the single most
valuable thing still missing for unattended play.

## Tool bug found and fixed

`mgba_diff_memory` threw `r.changes is not iterable` on a **zero-match** diff. `json.lua` encodes
an empty Lua table as `{}` rather than `[]`, and the TypeScript iterated it unguarded. Ironically
the error *was* the answer — zero changes is what proved the roster mirror frozen.

Fixed in `src/tools.ts` (normalise `changes` and `shown` via `Array.isArray`), rebuilt clean.
**Uncommitted** as of this writing. **Not active in this session** either — the MCP server
process was launched at startup, so the fix only takes effect after a restart.

# Phase 5 — the modal / input-active flag: `0x0202521B`

Rather than wait for a scripted event, I used a **repeatable, reversible** modal as a proxy:
pressing `Start` on the map opens the objective window, which swallows map input the same way
dialogue does.

Method — toggle and keep only what reverts:

1. Snapshot the state region `0x02024000` (8 KiB). EWRAM-wide gave 3723 changes; the narrow
   region gave **81**.
2. `Start` → diff → `0x0202521B` stood out as a clean `0 → 1`.
3. `B` → it returned to `0`.
4. Re-tested on a completely different modal (`A` on a unit): `0 → 1`, then `B` → `0`.

Two unrelated modals driving the same byte is what makes this Confirmed rather than a
single-sample guess — the exact standard the earlier `0x0202BC0A` and `+0x43/+0x45` mistakes
failed.

| State | `0x0202521B` |
|---|---|
| Free map cursor | `0` |
| Objective window open | `1` |
| Unit selected / menu open | `1` |

**Honest limitation:** not tested against a scripted event dialogue, which is the case that caused
the original detour and the one it most needs to cover. Flagged in `RAM.md` rather than assumed.

## Bonus: the text buffer yields unit names too

With the cursor on Priscilla, `0x0202A5B4` read `"Priscilla"`; backing out returned it to
`"Floor"`. So that one address answers **"who or what is on this tile?"** by name.

It also retroactively confirmed an inference made from raw stats alone: roster slot 10 (17 HP,
Def 3, Res 7, item `0x4B`) had been guessed to be a healer purely from its stat shape, and
Priscilla is a healer.

## Combined effect on the screenshot rule

Between the terrain/name buffer and this flag, the two things screenshots were being used for —
reading labels and identifying game state — are now both available from memory. **The labeling
allowance is, in practice, no longer needed.** Menu-label text is the last untested case.

# Phase 6 — retracting the modal flag, and what actually works

## `0x0202521B` was over-claimed

Phase 5 recorded it as "`1` = a window or menu is up." **That is wrong.** The counter-example:

`A` on an empty tile opened the field menu — `0x0202517C` read `count=5, index=1, state=1`, and a
`Down` press moved its index rather than the cursor, so it was unambiguously open — while
`0x0202521B` sat at **`0`**.

Confirmed states now:

| State | `0x0202521B` |
|---|---|
| Free cursor | `0` |
| Objective window (`Start`) | `1` |
| Unit selected | `1` |
| **Field menu** | **`0`** |

Downgraded to Unverified in `RAM.md`, with an explicit "do not use as an input-live test."

**This is the third theory of this shape to break** — `0x0202BC0A` (cursor), `+0x43/+0x45`
(has-acted), and now this. The common pattern: correct across two or three samples, broken by the
fourth. The lesson I keep re-learning is that **two confirmations are enough for a *location* but
not for *semantics*.** A location either holds the value or it doesn't; a claim about meaning has
to survive the cases you didn't think to try.

## The cursor-agreement heuristic also failed

`0x0202BBCC` and `0x0202BBD0` **agreed** at `(9,7)` while the field menu was open. So agreement
does not imply cursor control. Demoted to a weak hint.

## What does work: the input-signature probe

Snapshot the 8 KiB state region at `0x02024000`, press a direction, diff:

| Signature | State |
|---|---|
| ~41 changes incl. `0x0202BBCE` | free cursor |
| ~5 changes incl. an adjacent index/mirror pair | menu open (and this *locates* it) |
| ~10 changes, neither | input swallowed (event / animation) |

Three calls, distinguishes all three states, and finds the live menu slot as a side effect. Given
that menu slots are dynamically allocated anyway, this is the primitive to build on — not a magic
flag.

## Objective text is NOT in RAM as ASCII

Searched EWRAM for `"Defend"` with the objective window open: **zero matches**. `"Nils"` was also

**transient staging**, not a persistent table.

So the decoded-ASCII buffer covers terrain names, unit names, and dialogue lines, but **not**

Enemies started 8–11 tiles away (my units y 1–7, enemies y 14–22), so I ended a turn to close

## What happened

- **Allied reinforcements arrived** (the dialogue *"We'll serve as your reinforcements."* was
  literal): a live unit appeared at slot 29, `0x0202C578`, roster `0x1E`, class `0x2B`, level 1.

## Combat effects — mapped from one round

The allied reinforcement got attacked, and its diff gives the whole combat signature at once:

| Offset | Change | Meaning |
|---|---|---|
| `+0x13` | 28 → 19 | current HP — **9 damage** |
| `+0x09` | 0 → 6 | **experience +6** |
| `+0x1F` | 20 → 18 | **weapon uses −2** |
| `+0x28` | 181 → 184 | **weapon rank exp +3** |

**`+0x28` is upgraded Inferred → Confirmed.** It had been a plausible-looking guess based on `0x1F`
appearing at the sword slot for Lyn and the axe slot for brigands; watching it increment by 3 in
the same diff as weapon-use consumption is the direct evidence that was missing.

## Unit death

```
+0x13  current HP  -> 0
+0x0C  flags       -> 0x05
+0x32..+0x36       -> zeroed (inventory tail)
+0x3C  pointer     -> zeroed
```

Note `+0x00` (character pointer) was **not** cleared at death, so it can't be used as a liveness
test. Use `+0x13 == 0`.

## New hypothesis: `+0x46` is a distance/threat metric

When the 18 reinforcements spawned, `+0x46` dropped on **about a dozen player units
simultaneously** (`15→12`, `14→12`, `16→14`, …). A value that moves on nearly every unit the
instant enemies appear nearer looks like cached distance-to-nearest-enemy. Unverified, but it
would be directly useful for AI decisions, so it's worth chasing.

This also plausibly explains the old `+0x43`/`+0x45` mystery: that whole `+0x43..+0x47` block may
be per-unit AI/threat bookkeeping rather than status flags.

## Method lesson: counts lie, lists don't

I twice concluded "no new player unit" because the char-pointer search returned **29** both before
and after. Wrong: **one unit died and one arrived**, so the count was stable while membership
changed — `0x0202C3CA` left the list, `0x0202C57A` joined it.

This is a new flavour of the same recurring error: I trusted a **summary statistic** where the
underlying set had changed. Diff the addresses, not the count. Now recorded in `RAM.md`.
