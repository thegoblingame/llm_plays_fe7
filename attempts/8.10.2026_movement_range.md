**State on arrival:** Ch.22 Hector mode, turn 4, player phase (`0x0202BC07 = 0x00`), cursor at
`(12,2)` on Hector. Same position the previous session stalled in.

**Task:** retry the movement-range hunt using the `exclude=` set subtraction added in `736a34a`.

**Result: found.** IWRAM `0x030004AC`, a 27 × 24 grid behind a row-pointer table at
`0x03000440`. Full write-up in `RAM.md`; this file is the process record.

## What actually went wrong before

The previous four attempts were not bad hypotheses. Attempt 4 — "diff IWRAM on selection, 3580
changes, useless" — had the target in hand and threw it away, because **nobody measured the
noise floor**.

Measured this session:

| | Changed bytes |
|---|---|
| IWRAM, idle, doing nothing | **3402** of 32768 |
| IWRAM, on selection, raw | 4466 |
| IWRAM, on selection, minus noise floor | **1147** |
| EWRAM, idle, doing nothing | **9** |

So "3580 changes" was ~3400 noise + ~180 signal. The number looked like a wall and was actually
a nearly clean result wearing a disguise. The grid appeared as an unbroken run of
`0x00 → 0xFF` in the very first page of noise-cancelled output.

**Rule:** a diff count in a hot region means nothing until you have the do-nothing count to
subtract from it.

## Method

```
snapshot IWRAM as "base"           (nothing selected)
wait                               (free — no pause on this build, emu free-runs)
diff "base" -> store_as "noise"    (3402 addresses = the floor)
press A                            (select Hector)
verify +0x0C bit 0 == 1            (confirm by effect, not by assumption)
diff "base" exclude="noise"        (1147 survivors)
```

Same procedure on EWRAM in parallel, which is how the second map layer turned up.

## Reading the structure

The pointer table gave it away before any value analysis: 27 consecutive `0x030004xx` pointers
at stride `0x18`, and the last one plus 24 lands exactly on... the byte after the data. The
table ends precisely where its data starts. That is a `u8* rows[]` allocation and it dates the
whole structure in one glance.

Values decoded as pure Manhattan distance from the unit, `0xFF` elsewhere.

## Confirmations (deliberately not just two)

1. **Hector `(12,2)`, Move 5** — origin `0x00` at row 4, col 12.
2. **Roster 08 `(10,3)`, different x *and* y** — origin at row 5, col 10; row `y=0` read
   `5 4 3 4 5 6` across cols 8–13, exactly Manhattan from `(10,3)`. This is the control that
   pins the indexing; one unit alone could not distinguish `row = y+2` from a coincidence.
3. **Cross-source.** Hector's grid marks `(12,3)` unreachable and `(11,3)` cost 2. The previous
   session had independently read those two tiles as `"Wall"` and `"Floor"` out of the decoded
   text buffer. Unrelated mechanism, same answer.

Per the standing rule that two confirmations settle a *location* but not *semantics*, the third
is the one that matters — it tests meaning against a source that cannot share the same failure
mode.

## The trap, caught by trying to be tidy

Pressed `B` to leave the game clean, then re-read the grid out of habit. **It still held the
deselected unit's data**, on two reads seconds apart, with `+0x0C` back to `0x00`.

The buffer is zeroed at map init and thereafter only overwritten — never cleared. So reading it
without checking selection state returns a stale but completely plausible map. This is the
failure mode that would have been hardest to catch later, because nothing about the output looks
wrong.

Recorded in `RAM.md` with the gating rule.

## Side findings

  zeros while a unit was selected. Not terrain, not movement. Its table pointer sits at
  `0x03000438`, immediately before the movement grid's — so layers are catalogued together and
  the missing terrain array is probably another table of this exact shape. Better lever than
  searching for terrain IDs.
- **The old Hector-won't-move puzzle is settled as far as range goes:** `(11,3)` was reachable
  at cost 2. Not range, not terrain. Dropped input is the remaining explanation — untested.
- `advance_frames` costs a bridge round-trip *per frame* on this build; a 120-frame call ran
  over two minutes and had to be backgrounded. Unnecessary anyway, since there is no `pause`

# Part 2 — moving a unit (works)

Grant asked whether units can actually be moved now. Tested rather than guessed.

**Result: yes.** Legault `(10,3)` → `(11,6)`, committed with `Wait`. Full procedure now in
`RAM.md`. `+0x0C` went `0x00` → `0x01` (selected) → `0x42` (spent), position updated to `(11,6)`,
and `0x0202BD48` recorded roster 8 with origin `(10,3)`.

The move itself was never really in doubt. What changed is that **step 5 — read the grid before
pressing — makes a failure diagnosable.** The old Hector puzzle was unsolvable because out of
range, blocked path, and dropped input were indistinguishable. Now a non-`0xFF` destination that
fails to move is *necessarily* an input problem.

## Two corrections to Part 1, both caught by testing rather than reasoning

**1. `value != 0xFF` is not "I can stop here".** I wrote that in Part 1 straight off the
structure. It's wrong. With Legault selected, row `y=2` read `3 2 1 2 3 4` across cols 8–13 —
and cols 9, 10, 12, 13 held four live allies. The grid is the *pathfinding cost* map; you route
through allies, you don't stop on them. Legal destination = `value != 0xFF` **and** tile
unoccupied.

This is the exact failure shape the meta-lesson warns about: a claim about *semantics* asserted
from a structure that only supports a claim about *location*. Two units confirmed the layout;
neither tested occupancy, because I didn't think to.

**2. Values are not Manhattan distance.** Row `y=6` read `6 5 4 5 6` at cols 9–13 where Manhattan
gives `3 4 3 4 5`. Column 10 was blocked, forcing the path through column 11. In Part 1 every
populated cell happened to equal Manhattan, which made it tempting to describe the grid that
way. Read the value; never recompute it.

## Bonus: menu labels are in the text buffer — Confirmed

`RAM.md` listed this as "worth pursuing, untested". With the action menu open on its last entry,
`0x0202A5B4` read `"Wait"`.

So the highlighted menu entry is readable **by name** before pressing `A`. Committing the move
used both the struct (`count=3, index=2`) and the label (`"Wait"`) — two unrelated sources
agreeing, rather than leaning on "Wait is always last".

This closes the last routine use for labeling screenshots. None were taken this session.

## Why the attack didn't happen

Nearest enemy is at `(11,8)`, HP 23 — Manhattan 6 from Legault, whose Move is 6. Looked
reachable. **The grid said otherwise:** row `y=7` is entirely `0xFF`, a wall spanning it, and
Legault's reach bottoms out at `y=6`.

Worth noting how that went: I learned the attack was impossible **without pressing anything**.
Under the old method this would have been a cursor walk, a failed `A`, and another round of
guessing which of three causes it was.

Legault is now parked at `(11,6)`, two tiles from that enemy, which sets up the combat forecast
next turn — he is also now exposed, which is fine and probably informative.
