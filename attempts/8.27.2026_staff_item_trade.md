## 4. Target readback

The gap the caller flagged. Answer: **`gBattleTarget` is not it for staves.** During staff
target select `0x0203A474` (class pointer) read `0`, i.e. RAM.md's own staleness gate
correctly says "don't read this". It *is* populated after the staff resolves.

What works, three independent instances:

**(a) Signature lookup, staff only.** The staff target-select proc has ROM script pointer
`0x08B96998` at its `+0x00`, and the highlighted target's unit-struct pointer at `+0x2C`:
```
search_memory(bytes=[0x98,0x69,0xB9,0x08], region="EWRAM", align=4)
  -> exactly 1 match while in staff target select, 0 matches otherwise
target = read32(match + 0x2C)
```
Samples: proc @`0x02025338` -> `0x0202BEB8` (Bartre); proc @`0x0202511C` -> `0x0202DCD0`
(green NPC), then `0x0202BF00` after one `Right`. The proc address is **dynamic**.

**(b) Diff lookup, general.** Snapshot `0x02024000`+8192, press `Right`, diff `width=4`.
The one slot holding a unit-struct address that changed is the live highlight. Worked for
staff target (`0x02025148`), trade partner (`0x02024F2C`) and rescue target (`0x020251B4`).

**Green/NPC units are valid staff targets** — the initial highlight at (10,2) was
`0x0202DCD0`, the green array's slot 0.

## 6. Negative results

- **Menu labels are not ASCII in EWRAM.** With the action menu open,
  `search_memory(text="Staff")` and `text="Trade"` both returned **0 matches**. Labels are
  rendered as VRAM tiles.
- **`0x0202A5B4` does not track the action-menu highlight.** It read `"Wait"` at index 2 of 4
  and again at index 0 of 4. HANDOFF's correction is right and this closes it: the action
  menu has no description panel, so nothing re-renders. It *does* track the item/staff list
  highlight, because that list has a description panel.
- **The menu struct's `+0x03` state byte is unusable in both directions.** Read `0x05` on a
  menu that was live and driving input, and `0x00` on the item sub-menu that was live.
- **There is no fixed proc-script signature at a fixed offset from a menu struct.** The word
  at action-menu`+0x14` read `0x08B9A8E0` at one moment and `0x08B908D0` a few frames later.
  A search for `0x08B9A8E0` returned 5 hits, not "one per open menu".
- **`0x020253D0` (trade proc `+0x28`) is the *initial* partner and goes stale** — it stayed on
  Raven across three `Right` presses while the real highlight moved. Classic
  location-is-not-semantics trap; the live value was elsewhere.
- **A diff taken immediately after `press_sequence` returns often catches a mid-transition
  frame** (30-70 changes of sprite/OAM churn). Re-running the same diff a few seconds later
  returned the settled 4-7 changes with the index pair clearly visible. Diff twice.

## 7. Operational gotchas

- **A level-up blocks the spent flag.** After the second heal, `+0x0C` stayed `0x01` and the
  staff uses stayed unchanged for two consecutive reads. ASCII read `"Lucius"` +
  `"...increased."` — a level-up screen. After `A`x3 the unit committed: level 2->3,
  exp 99->4, Skl +1, uses 6->5, `+0x0C` -> `0x02`. **Poll `+0x0C` bit 1 and press `A` until
  it sets**; do not treat the first read as final.
- **EWRAM idle noise in `0x02024000`+8192 is ~5 bytes**: `0x02024C84`, `0x02024C8A`,
  `0x02024C8B`, plus one 16-bit counter whose address moves between allocations
  (`0x02025154/55`, `0x02025010/11`, `0x020253DC/DD` all seen). Anything else in a
  post-direction-press diff is signal.
- **Menu allocation slots seen today**: `0x0202532C`, `0x02024F60`, `0x020256F8`,
  `0x020250A4` for the *action* menu alone, plus `0x02025470`, `0x02025548`, `0x020252C0`,
  `0x020255B4`, `0x020256F8` for lists and sub-menus. `0x020252C0` was read as a *stale*
  copy of a sub-menu while the live one sat at `0x020256F8`. Locate by diff, every time.
